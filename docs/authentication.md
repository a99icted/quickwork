# Авторизация

Access-токен — подписанный JWT для обычных запросов к API. По умолчанию он действует **15 минут** (`ACCESS_TOKEN_EXPIRE_MINUTES=15`) и передаётся в заголовке `Authorization: Bearer ...`. Фронтенд хранит его только в памяти: после перезагрузки страницы он исчезает. JWT подписан, но не зашифрован: его содержимое можно прочитать, поэтому пароль и другие секреты в него не помещаются.

Refresh-токен позволяет получить новый access-токен без повторного ввода логина и пароля. Это длинная случайная строка, которая по умолчанию действует **7 дней** (`REFRESH_TOKEN_EXPIRE_DAYS=7`). Браузер получает её в cookie `qw_refresh` с `HttpOnly` и `SameSite=Lax`; JavaScript не может прочитать эту cookie. При HTTPS включается также `Secure`. Сервер хранит только SHA-256-хеш токена, а не исходную строку.

Последовательность работы:

1. `POST /auth/login` проверяет пароль, возвращает `access_token`, `token_type`, `expires_in` и устанавливает refresh-cookie.
2. Обычные запросы используют access-токен. При `401` клиент один раз вызывает `POST /auth/refresh`, получает новый access-токен и повторяет исходный запрос. Параллельные запросы в одной вкладке используют одно обновление; между вкладками обновления сериализуются через Web Locks, если браузер их поддерживает.
3. При перезагрузке страницы клиент восстанавливает вход через ту же refresh-cookie. Ни access-, ни refresh-токен в `localStorage` не записываются; старое значение `token` удаляется при загрузке.
4. Каждое успешное обновление **заменяет refresh-токен**: предыдущий отзывается, новый записывается в cookie. Срок всей сессии отсчитывается от входа и не продлевается бесконечно.
5. Повторное предъявление уже использованного refresh-токена отзывает всю цепочку этой сессии. Это помогает ограничить использование украденного токена. Другие независимые входы сохраняются. Для новых токенов потребуется снова войти.
6. `POST /auth/logout` отзывает цепочку на сервере и удаляет cookie, даже если access-токен уже истёк. Выход требует доступного сервера; при сетевой ошибке интерфейс сообщает о ней и позволяет повторить действие.

Разделение нужно для удобства и ограничения времени доступа: пользователь остаётся в аккаунте несколько дней, а утечка одного access-токена даёт доступ только до его ближайшего истечения. Refresh-токен обычные API-методы не принимают. Уже выданный access-токен после выхода действует до истечения своего короткого срока; мгновенного отзыва JWT в этой демоверсии нет. HttpOnly уменьшает риск чтения refresh-токена через JavaScript, но не заменяет защиту приложения от XSS.

Для `/auth/login`, `/auth/refresh` и `/auth/logout` сервер проверяет браузерный `Origin`; ответы с токенами и удалением cookie имеют `Cache-Control: no-store`. Все маршруты также доступны с префиксом `/api`.

Настройки задаются в `server/.env`; пример — в [`server/.env.example`](../server/.env.example). Для HTTPS установите `COOKIE_SECURE=true`. Фронтенд и API должны находиться на одном сайте; рекомендуемая схема — общий адрес с API по `/api`.
